# V1.4.0 Implementation Summary

## Goal

Create one coherent academic network instead of maintaining two isolated chains (`Batch → Group → Student` and `Lecturer → Subject`).

## Final model

`Term + Subject + Lecturer + Batch/Group → Course Offering → Enrollment → Student`

This avoids a technically incorrect direct Lecturer → Student relationship and creates the correct foundation for V1.5 Attendance and V1.6 Grades.

## Implemented modules

### Terms / Semesters
- Create and edit terms.
- Dates, code and status.
- Dedicated term profile.
- Direct navigation to term course offerings.

### Course Offerings
- Create and edit a real class instance.
- Required Subject + Term.
- Optional Lecturer, Batch and Group.
- Server validation that Group belongs to the chosen Batch.
- Group selection automatically inherits its Batch when Batch is omitted.
- Filter by term, subject, lecturer, batch, group and status.
- Dedicated profile with connected academic map and roster.

### Enrollment
- Real `Student ↔ Course Offering` relationship.
- Unique student/offering protection prevents duplicates.
- Enrollment only accepts ACTIVE students into ACTIVE offerings.
- Eligibility follows Group first, otherwise Batch, otherwise open enrollment.
- Statuses: ACTIVE / DROPPED / COMPLETED.
- Central enrollment directory and per-offering roster.

## Permissions

Six new granular permissions were added:
- `terms.view`
- `terms.manage`
- `offerings.view`
- `offerings.manage`
- `enrollments.view`
- `enrollments.manage`

OWNER and ADMIN inherit the new permissions under existing role rules. DATA_ENTRY and VIEWER receive the three view permissions by default; management remains explicitly controlled.

## Database changes

Schema v3 adds:
- `academic_terms`
- `course_offerings`
- `enrollments`
- 7 targeted indexes

Migration: `migrations/0002_academic_network.sql`

The migration is additive/non-destructive.

## Existing data preserved

No existing Batch, Group, Lecturer, Subject, Student, User, Permission override, Session or Audit table was removed.

`subjects.lecturer_id` remains available for backward compatibility and is now treated as a default lecturer, while real teaching assignments live on Course Offerings.
